# Art Server API — Contract for the Director/UI

The **server** (`art_server.py`) is the generation engine. It runs on the machine
with the GPU (currently `100.82.167.121` on Tailscale, `192.168.87.43` on LAN),
binds `0.0.0.0:8090`, and exposes the HTTP API below.

Your job (the **director/UI** component) is to build the client that talks to one
or more of these servers: display the gallery, edit configuration, and submit
generation jobs. Treat every endpoint below as stable — code against this
contract, not against the server's internals.

---

## Base URL

Each server is addressed by its own `ip:port`. In a multi-server setup the
director keeps a **list** of base URLs and load-balances across them.

```
http://<server-ip>:8090
```

Example (current server over Tailscale): `http://100.82.167.121:8090`

---

## Auth

If the server's config has a non-empty `auth_token`, the API endpoints
(`/generate`, `/jobs`, `/config`, `/health`) require one of:

```
Authorization: Bearer <token>
X-Auth-Token: <token>
```

Static gallery (images, `gallery.html`, `/images`, `/index.json`) is **always
open** so browsers can view art without a token.

## Endpoints

### `GET /health`

Server status + capacity. **Use this to pick which server to send work to.**

```json
{ "status": "ok", "busy": false, "queue_depth": 0, "gallery_count": 50 }
```

- `busy` = a job is queued or running right now
- `queue_depth` = jobs waiting to start
- Director rule of thumb: send new work to a server where `busy == false`.

### `GET /config`

Current generation settings.

```json
{ "steps": 20, "guidance_scale": 7.5, "width": 768, "height": 448, "auth_token": "" }
```

### `PUT /config`

Update settings. Body is a partial object — only the keys you send change.

```json
{ "steps": 25, "width": 640 }
```

Returns the full updated config. Persisted to disk, survives restart.

### `POST /generate`

Submit a generation job. **`prompt` is required.** Everything else is optional
and falls back to the server config.

```json
{
  "prompt": "a serene mountain lake at dawn, mist",
  "steps": 20,
  "guidance_scale": 7.5,
  "width": 768,
  "height": 448
}
```

Response (HTTP `202`):

```json
{ "job_id": "220d3c4facd7", "status": "queued" }
```

Generation is **async** — the server has a single worker that processes jobs
one at a time (SD 1.5 holds the GPU). A job takes roughly 5–20s depending on
`steps` and resolution.

### `GET /jobs/<job_id>`

Poll for the result.

```json
{
  "id": "220d3c4facd7",
  "status": "done",            // queued | running | done | failed
  "prompt": "a serene mountain lake at dawn, mist",
  "params": { "steps": 20, "guidance_scale": 7.5, "width": 768, "height": 448 },
  "image": "art_20260829_122608_706420e4.png",   // null until done
  "error": null,                                  // set when status == failed
  "created": 1760000000.0,
  "finished": 1760000012.0
}
```

Poll every ~2s until `status` is `done` or `failed`. On `done`, fetch the image
at `GET /<image>`.

### `GET /jobs`

List all jobs (newest first).

```json
{ "jobs": [ { ...same shape as above... } ] }
```

### `GET /images`

Gallery metadata, newest first.

```json
{ "images": [ { "timestamp": "...", "prompt": "...", "style": "SD 1.5", "file": "art_....png" } ] }
```

### `GET /index.json`

Same metadata as `GET /images` but in the original newline-delimited-JSON format
(one JSON object per line) that the existing `gallery.html` already consumes.

### Static files

- `GET /` → `gallery.html` (the viewer UI)
- `GET /<file.png>` → a generated image

## Multi-server / one-director model

The director should:

1. Hold a **configurable list of server base URLs**.
2. On startup (and periodically), call `GET /health` on each.
3. Route a new `POST /generate` to a server reporting `busy == false` (round-robin
   among idle servers).
4. Aggregate galleries by merging `GET /images` from all servers.
5. Persist each server's config via `PUT /config`.

This makes "several servers, one director" work with zero server-side changes —
servers are interchangeable peers.

---

## What the server already handles (don't reimplement in the client)

- Async job queue + serialized GPU generation
- Watermarking ("Generated by Local AI")
- Writing + pruning `index.json` metadata
- Path-traversal protection on static file serving
- Chunked + Content-Length request body parsing
- Optional token auth

## What's deliberately NOT in the server (your side)

- Any UI beyond the existing `gallery.html`
- Prompt library / scheduling / "director" logic
- Multi-server load balancing
- Image editing / deletion / re-generation history
